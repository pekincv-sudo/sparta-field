# SPARTA field deploy package

This folder is the clean static web app for deployment.

## Local development

The current work is a clean local data-entry workspace. Open `http://127.0.0.1:4174/?build=36`.
On `localhost`, `127.0.0.1` and `::1`, `local-workspace.js` disables Supabase
initialization. Projects, inventory, tasks and cash use the independent
`sparta.local.v1.*` browser storage; local file blobs use
`sparta-local-project-files-v1` in IndexedDB.

New workspaces start empty. Historical browser records are not automatically
imported, and no demo objects, catalog, tasks or cash are seeded. Authentication,
company configuration and calculator preferences remain separate from operational
data. Do not clear browser site data if you want to keep the local database.

On 24 October 2026 the disposable local records were backed up, verified and
removed through the local maintenance panel. The profile provides download access
to the pre-clean backup. See `docs/CLEAN-START-build33.md` for exact scope and
recovery information. The demo generator, sample files and demo UI are no longer
part of this app.

The cash journal is available in installer mode under **Каса**. Entries record
UAH kopecks, payment date/time in Kyiv, counterparty, purpose, project, payment
method and creation time. Corrections use linked reversals. CSV export respects
the selected filters. New client payments minus refunds reduce the project's
outstanding balance; prior `finance.advancePaid` remains a separate opening
amount. Enter only new payments in the new journal. Cash expenses show money
movement; estimated material/payroll costs remain in the project cost estimate
and are not counted twice.

To check the financial rules with Node.js, run `node tests/run-tests.js`.
The tests use isolated data and simulated services and do not access Supabase.

## Public release 34

The existing Vercel project serves `public-build/`, generated by
`node scripts/build-public.js`. SQL, tests, documentation and historical ZIP
archives are excluded from the static output; existing `/api` functions remain
in the repository root. `vercel.json` defines the build and output directory.

Apply the existing-project upgrades in this order:

1. `database/release34-base.sql`
2. `database/project-save.sql`
3. `database/warehouse-cloud.sql`
4. `database/cash-transactions.sql`
5. `database/private-storage.sql`
6. `database/field-project-sync.sql`

Public startup requires a verified company membership and upgraded schema.
Browser business caches are scoped by user and company. Local browser data is
never automatically uploaded to production.

The warehouse uses company revision checks and idempotent requests to commit
stock documents, reserves and project material snapshots together. Office saves
commit project, technical and string data atomically. Media has a separate
revision check. Conflicting edits fail visibly instead of replacing newer work.
Storage buckets are private, with company/role policies and temporary signed
photo links. The cash journal is append-only and owner/admin scoped.

Owner/admin/warehouse can post warehouse documents. Office roles manage object
cards and material plans. Installers can update checklists and attach photos and
files without general financial edits. The client switch remains a staff preview;
customer-specific object ownership and inverter telemetry are separate future
integrations. Solar estimates are calculations, not live inverter readings.

For the explicitly disposable test dataset, `database/archive-test-data.sql`
provides a private administrator-only snapshot and an idempotent clean start.
It retains auth/company accounts and storage blobs. Restore is allowed only into
an empty company and never overwrites newly entered data. It refuses to remove
posted cash history. See `docs/PUBLIC-RELEASE-build34.md` for the release record.

Run `node tests/run-tests.js` for browser-domain/service adapter tests. Optional
`*.sql.test.js` tests execute the actual migrations in PostgreSQL via the
PGlite development dependency supplied in `PGLITE_MODULE`; this dependency is
not part of the production app. `SPARTA_BASE_SCHEMA` points to the original
schema fixture.

## Repeat-buyer cabinets — build 38

Public staff now manage external purchasers under «Продажі». Buyers have separate membership and see only their own catalog price tier, orders and purchase history. Retail, installer and wholesale prices are independent; the account tier is assigned by owner/admin. Confirmation reserves stock; fulfilment deducts it once, without an automatic cash entry. Apply `database/buyer-portal.sql` before the frontend. See [buyer rollout and operations](docs/BUYER-PORTAL-build38.md).

## Catalog and opening-stock import — build 39

Owner/admin/warehouse users can import a prepared UTF-8 semicolon CSV through Warehouse → Other operations → Import nomenclature. The preview validates fixed currencies, variants, matching existing cards and explicit 100-unit additions, then requires a downloaded current warehouse backup. One authenticated warehouse transaction posts the whole batch; deterministic source/document identities prevent adding it again after a reload or lost response. Posted documents and actor history remain intact.

Required columns: `name;sku;unit;category;currency;purchasePrice;installerPrice;retailPrice;wholesalePrice;qty;sourceRow`. Blank prices remain unset; zero is distinct from missing. Source currency is explicit USD or UAH; prices are never converted or relabelled. Existing cards retain sale tiers, unit costs and reservations. New known-cost goods get an opening receipt; new goods with unknown acquisition cost get an explicitly unvalued opening adjustment. Such cards show “Не задано” for unit cost, and affected documents state that valuation is incomplete. Warehouse stock entries create no cash payment. Spreadsheet selection/conversion is reviewed before import; source catalogs are not bundled or seeded in the public application.

## Product photographs — build 40

Warehouse stock/catalog rows, item details and buyer catalog/cart show locally bundled, optimized product photographs. `product-photos-data.js` contains opaque reviewed name aliases and source credits only; it includes no source-spreadsheet prices. Matching is exact after whitespace/case normalization. New similar product names do not inherit another model's photograph. Item details distinguish a model photograph from a series or illustrative type photograph and link to the source and full image. Missing media has an explicit fallback. The photo layer is read-only and does not change quantities, documents, prices, reservations or permissions.

## Solar Dash — build 41

The existing sun-catching mini-game opens from «☀ Гра» in the staff toolbar and buyer header. SPARTA Power logos appear on its start/end overlay and in-game HUD. The game loads on demand inside an opaque-origin iframe (`sandbox="allow-scripts"`); it receives only a throwaway session ID and a numeric best score, never application credentials or company data. Closing or losing access removes the frame and stops its animation. Personal records are stored on the current device under an explicit user/company scope; they do not synchronize between devices. Storage failures keep play available with a memory-only record notice. No cash, stock, rewards or leaderboard writes are made.


## Warehouse Excel round trip — build 42

Warehouse offers «Експорт Excel» and «Завантажити Excel» in public and local workspaces. The .xlsx file contains all physical catalog rows (independent of screen filters), stable IDs, explicit currencies/units, final stock quantities, catalog details and three sales price tiers. It also includes editing instructions and a hidden baseline snapshot. SheetJS CE 0.20.3 is bundled from its official CDN and loads only on demand; no workbook is sent to a third-party service.

Imports show old/new quantities and changed field values before confirmation. Final quantity is an absolute count, never an additive receipt. Existing currency/unit and acquisition costs remain fixed; blank numeric edits retain the old value, explicit zero is zero, and absent rows do not delete goods. New rows use blank IDs and explicit units/currencies; their acquisition cost is marked unknown. Formulas must be pasted as values.

Only owner/admin/warehouse can import. The company/local scope is checked, edited rows must still match their export baseline, combined buyer/project reserves are protected, and serialized quantities require ordinary stock documents. All changes commit atomically through the existing warehouse transaction, with posted stocktake audit documents per currency. Content-based batch IDs prevent repeated application even after subsequent stock movements. Prices/snapshots in earlier orders or object issues, cash and historical documents remain unchanged. No SQL migration is required.

Validation: 424 JavaScript checks including 48 Excel core/real-XLSX/UI checks. Browser QA used isolated localhost4180: export, new row, quantity12→15 and retail120→125, persistence after reload and repeated-file handling. Production QA exports and previews the unchanged live workbook without altering business data.
